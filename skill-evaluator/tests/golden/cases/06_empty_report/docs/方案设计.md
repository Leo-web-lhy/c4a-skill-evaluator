# C4A 技能提交自动评审 · 方案设计

学号：2023108610260

## 1 问题与边界

技能提交一直是人肉判断，同一份提交两个人打分能差 20 分，且没人说得清扣分来自哪里。本方案只解决三个问题：必交物是否真的存在、结构证据是否齐备、扣分能否指到具体文件的具体行。

明确不做的三件事：不评价方案语义质量、不自动拒绝任何提交、不替代教师打分。

## 2 架构

四层单向依赖：

1. 采集层 collect：遍历目录，跳过 .git / node_modules，产出确定性排序的清单。
2. 必交物层 deliverables：按平台同名规则（文件名通配，不看内容）判定是否存在与是否空壳。
3. 探针层 signals：regex / absent / exists / size / count_files 五类探针，每条探针必须带证据。
4. 评分层 scoring：维度封顶 + 红线封顶 + 复核建议。

## 3 评分

五个维度：评审器质量 25、技术实现 20、产物完整性 15、AI 使用质量 20、复盘质量 20，合计 100。

维度分只在探针命中且有证据时累计，且不超过维度上限。原始分超过上限时记 capped=true，避免"堆探针刷分"。

## 4 证据链与可复现

无 LLM 调用、无网络、无时钟、无随机数，因此同一目录必然产出同一结论。

每条结论都带 evidence（文件路径 + 行号 + 片段），报告头部记录 evidence_hash，取值为「版本号 + 每个文件的路径 / 字节数 / SHA-256」的哈希，任何人可以独立复算。

## 5 误判控制

- 宁可漏判，不可误判：探针没有证据就不给分。
- 红线只做封顶，不做拒绝：触发后仍需人工确认。
- 空壳判定阈值 20 字节，避免把 0 字节占位文件当成交付物。
- 文件名匹配与平台一致，避免"平台判 missing、工具判 present"的双标。

## 6 人机边界

工具输出「扣了哪些分、证据在哪、需要人看什么」，最终打分与放行由人和教师决定。

## 7 交付形态

- skill-evaluator/：可独立运行的评审器
- rubrics/c4a.json：评分标准外置，可替换
- tests/golden/：带期望值的用例
- 评审报告.md：真实提交上的运行结果
- AI日志.md / AAR.md：协作记录与复盘
