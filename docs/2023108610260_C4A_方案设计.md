## 1. 问题与边界

### 1.1 真实问题

C4 系列挑战要求提交"技能"，但"技能好不好"一直是人肉判断：看 README 顺不顺眼、翻两眼代码、凭印象打个分。这带来三个具体后果：

1. **不可复现**：同一个人隔一天看同一份提交，分数可能不同；两个评审者更难对齐。
2. **无证据**：给出"缺少使用说明"这样的结论时，指不出是哪一行、哪个文件。
3. **不可批量**：一次几十份提交时，逐份人工细读的时间成本压不住。

C4A 要求的正是把这个动作变成**可运行、可复核、有证据定位**的评审器。

### 1.2 我明确不做什么（非目标）

- **不做语义质量判断**。评审器不判断"这个技能是否有价值"、"文案是否打动人"，那是人的领域。它只判断**可机器核验的结构与证据**。
- **不做自动淘汰**。评审器输出的是"证据 + 扣分点 + 人需要复核的问题"，不是"通过/不通过"的终裁。
- **不调用大模型**。全程确定性规则，同一输入必然同一输出（第 6 节给出可复算的哈希证据）。理由是：评审器本身如果不可复现，就失去评审资格。

### 1.3 由谁来用

- 学生自己：提交前自查，避免"核心交付物缺失"这类低级扣分。
- 助教/教师：批量初筛，把注意力集中在评审器标出"需要人看"的位置。

## 2. 架构

```
输入：提交目录 + 挑战 rubric（JSON）
  │
  ├─ Layer 1 采集层  collect.py 行为
  │   遍历目录（跳过 .git / node_modules / __pycache__），
  │   记录每个文件的相对路径、字节数、行数、是否文本、扩展名。
  │   → inventory（不可变事实层）
  │
  ├─ Layer 2 必交物层  deliverables.py 行为
  │   按 requiredDeliverables 通配符（*方案设计* 这类，按文件名匹配）
  │   判定 found / missing / empty（< 20 字节视为空壳）。
  │   → 任一 missing 或 empty 触发红线 missing_artifacts
  │
  ├─ Layer 3 信号层  signals.py 行为
  │   在文本文件上跑一组确定性探针，每条探针产出
  │   {id, dimension, weight, hit, evidence:[{file,line,snippet}]}
  │   探针分四族：AI 协作 / 复盘质量 / 可运行性 / 工程规范。
  │
  ├─ Layer 4 评分层  scoring.py 行为
  │   维度分 = min(Σ命中权重, 维度上限)；红线按挑战定义封顶。
  │   每条扣分都必须带 evidence，无证据不得扣分。
  │
  └─ 输出：report.json（机读）+ report.md（人读）
```

关键设计取舍：**证据先行，分数在后**。实现上先产出 evidence 列表，再由 evidence 汇总成分数，而不是先打分再补理由。这样"没有证据的扣分"在结构上不可能发生。

## 3. 评分规则（对照 C4A rubric）

| 维度 | 上限 | 探针（命中才给分） |
|---|---|---|
| evaluatorQuality 评审器质量 | 25 | 评分标准外置为 JSON(4) / 有测试用例目录(5) / 自测报告含误判率与用例数(8) / 输出结构化机读结果(4) / 同一输入重复运行结果一致(4) |
| technicalExecution 技术实现 | 20 | 分层模块(4) / 无 TODO-FIXME 残留(3) / 含错误处理(4) / 代码规模与注释比合理(4) / 有版本号与变更记录(5) |
| artifactCompleteness 产物完整性 | 15 | 必交物全命中(6) / README 含安装与用法(5) / 可执行入口（CLI 或 main）(4) |
| aiUsage AI 使用质量 | 20 | AI日志存在且成规模(6) / 记录 ≥3 轮迭代(5) / 含 Prompt 或指令记录(5) / 记有失败与转向(4) |
| reflectionQuality 复盘质量 | 20 | AAR 存在(4) / 有具体卡点描述(6) / 有量化或可验证的改进方案(6) / 记录失败用例(4) |

红线（来自挑战定义）：

- `missing_artifacts` → artifactCompleteness 封顶 5
- `no_ai_log` → reflectionQuality 封顶 5
- `one_shot_ai`（AI日志 < 300 字且无迭代标记）→ aiUsage 封顶 5

## 4. 证据链格式

每条 evidence 是三元组 `(文件相对路径, 行号, 命中片段)`，例如：

```
ai.iteration_rounds  → docs/AI日志.md:42  "## 第 3 轮：把阈值从 20 字节改成可配置"
missing.aar          → (无命中) 期望文件名含 "*AAR*"
```

评审报告的每条扣分都必须能**双击打开对应文件的对应行**复核。这是本方案与"凭印象打分"的分界线。

---

## 5. 误判控制

1. **Golden Set**：手写 6 份合成提交（优等/缺 AAR/空文件/一句话指令/无 AI日志/过度声称），每份带人工标注的期望区间。评审器跑的分数必须落在区间内，否则记为一次误判。
2. **误判率口径**：`误判数 / 用例数`，按"维度级"统计（比总分更严格）；同时报"红线误报/漏报"。
3. **已知误判模式**：把 Golden Set 里踩到的每一种失败写进 AAR，而不是调参调到全绿。
4. **不在真实提交上调参**：真实提交只用于校准分析（与平台 AI 初评对比），不用于修改规则——否则就是对着答案改卷子。

---

## 6. 确定性验证

- 评审器不读时间、不用随机数、不联网（可加 `--offline` 断言）。
- 对同一目录连续运行 2 次，比对 `report.json` 的 `evidence_hash`（evidence 列表的 sha256）。相等即证明可复算。
- 证据在报告里落盘，任何第三方可用同一命令复跑并比对哈希。

---

## 7. 与平台 AI 初评的关系

评审器**不替代**平台初评，只提供第二条独立视角：

- 平台初评是语义模型，能读内容；评审器是结构规则，能查缺失与证据。
- 两者不一致的地方最有价值：平台给高分但评审器发现必交物空壳，或平台低分但结构证据齐全 → 那是人该看一眼的地方。
- 校准分析用我自己已出分的 6 份真实提交（C1 91 / C2 90 / C2G 86 / C5A 89 / C9 88 / 另有 2 份待回填）计算平均绝对误差与排序一致性，结果写进评审报告第 4 节。
